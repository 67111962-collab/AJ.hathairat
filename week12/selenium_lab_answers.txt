2) ระบุว่าสองแบบใดเจอช่องกรอกเดียวกัน
by_id เจอ: ช่องกรอกชื่อ (Student name)   
by_name เจอ: ช่องกรอกชื่อ (Student name)   
by_css เจอ: ปุ่มลงทะเบียน (Register)   
by_xpath เจอ: หัวข้อหน้าเว็บ (h1 ที่เขียนว่า "CE Course Registration")   
สองแบบที่เจอช่องเดียวกันคือ: by_id และ by_name (ค้นพบช่อง input student_name เหมือนกัน)   

1.2 ชื่อหน้าเว็บถูกต้อง บอกได้หรือยังว่าลงทะเบียนได้ถูกต้อง?
1) คัดลอกชื่อหน้าเว็บจากช่อง Actual
2) ตอบว่าแค่ชื่อหน้าเว็บถูกต้อง เพียงพอจะยืนยันว่าลงทะเบียนได้ถูกต้องหรือไม่ เพราะอะไร
3) บอกสิ่งที่ควรทดลองเพิ่มอีก 1 อย่าง เพื่อดูว่าลงทะเบียนได้จริงหรือไม่
ชื่อหน้าเว็บ: "CE Course Registration"   
เพียงพอหรือไม่ เพราะอะไร: ไม่เพียงพอ การตรวจสอบหน้าเว็บว่าถูกต้องเป็นเพียงการรับประกันว่าระบบโหลดหน้าลงทะเบียนมาถูกหน้า แต่มันไม่ได้รับประกันว่าการทำงานหรือระบบตรวจสอบข้อมูลตอนบันทึกลงทะเบียนนั้นถูกต้อง   
สิ่งที่ควรทดลองเพิ่ม: ควรลองกรอกข้อมูลให้ครบและกด Register เพื่อตรวจสอบผลลัพธ์ว่าระบบรับข้อมูลและแสดงข้อความ REGISTERED ได้จริงหรือไม่

2.1 เว็บตอบกลับอย่างไรเมื่อกรอกข้อมูลทั้งสามแบบ?
1) สำหรับแต่ละกรณี ให้คัดลอก Expected (ผลที่คาด), Actual (ผลจริง) และ Status (สถานะผลทดสอบ)
2) เขียนให้ครบทั้งสามกรณีตามรูปแบบในช่องคำตอบ
valid_form: Expected = REGISTERED / Actual = REGISTERED / Status = PASS  
 blank_name: Expected = NAME_REQUIRED / Actual = NAME_REQUIRED / Status = PASS  
 missing_consent: Expected = CONSENT_REQUIRED / Actual = CONSENT_REQUIRED / Status = PASS

2.2 ทำไมกรณีไม่กรอกชื่อจึงได้ PASS?
1) ตามกติกา เว็บควรรับหรือปฏิเสธการลงทะเบียนเมื่อไม่กรอกชื่อ
2) เทียบ Expected กับ Actual แล้วอธิบายสั้น ๆ ว่าเหตุใด test จึงได้ PASS
เว็บควร: ปฏิเสธการลงทะเบียน   
Expected กับ Actual ตรงกันหรือไม่: ตรงกัน (เป็น NAME_REQUIRED ทั้งคู่)   จึงได้ PASS 
เพราะ: การทดสอบนี้เป็นการตรวจว่าระบบปฏิเสธข้อมูลที่ไม่ถูกต้องตามเงื่อนไขหรือไม่ (Negative Testing) เมื่อเว็บปฏิเสธตามที่คาดหวังไว้ ผลทดสอบจึงได้ PASS

3.1 ค้นหาทันทีกับรอข้อมูลก่อน ได้ผลต่างกันอย่างไร?
1) บันทึก Status ของทั้งสองกรณี และ Actual ของกรณี explicit_wait
2) คัดลอกชื่อข้อผิดพลาดที่พบใน immediate_lookup เช่นชื่อที่ลงท้ายด้วย Exception หรือ Failure
3) อธิบายว่ากรณีแรกค้นหาก่อนข้อมูลพร้อม หรือเว็บทำงานผิด โดยใช้ผลของกรณีที่รอมาช่วยอธิบาย
immediate_lookup: Status = EXPECTED_FAIL / ชื่อข้อผิดพลาด = ดูในลิงก์ Traceback จะพบคำว่า EarlyLookupFailure หรือ NoSuchElementException   
explicit_wait: Status = PASS / Actual = COURSE_READY   
สาเหตุของกรณีแรกและหลักฐาน: กรณีแรกค้นหาก่อนข้อมูลจะพร้อม เนื่องจากเว็บต้องใช้เวลา 3 วินาทีในการแสดงข้อมูล แต่คำสั่งค้นหาทำงานทันทีทำให้หาไม่เจอ (เกิด NoSuchElementException) หลักฐานคือกรณี explicit_wait ที่มีการสั่งให้รอจนกว่าข้อมูลจะพร้อม สามารถค้นหาข้อมูล COURSE_READY เจอและได้ผล PASS   

3.2 ถ้าหยุดรอ 3 วินาทีเท่ากันทุกครั้ง จะมีปัญหาอะไร?
1) ถ้าข้อมูลเพิ่งปรากฏหลัง 5 วินาที แต่ test หยุดรอแค่ 3 วินาทีแล้วค้นหาทันที จะพบข้อมูลหรือไม่ เพราะอะไร
2) ถ้าข้อมูลพร้อมตั้งแต่วินาทีที่ 1 แต่ test ยังหยุดรอครบ 3 วินาที จะมีเวลารอที่ไม่จำเป็นหรือไม่
3) การรอจนข้อมูลพร้อมด้วย explicit wait ช่วยในสองสถานการณ์นี้อย่างไร
ข้อมูลพร้อมหลัง 5 วินาที: จะหาข้อมูลไม่พบและเกิด error เพราะ test หยุดรอแค่ 3 วินาทีแล้วค้นหาเลย ข้อมูลจึงยังไม่ปรากฏ   
ข้อมูลพร้อมหลัง 1 วินาที: จะทำให้เสียเวลารอโดยไม่จำเป็นไป 2 วินาที เพราะข้อมูลมาตั้งแต่ 1 วินาทีแรกแล้ว   
explicit wait ช่วยอย่างไร: ช่วยให้รอแบบยืดหยุ่น คือรอจนกว่าเงื่อนไขจะพร้อม เมื่อพร้อมแล้วก็ทำงานต่อทันทีโดยไม่ต้องรอจนครบเวลาสูงสุด

3.3 รอได้สูงสุด 10 วินาที หมายความว่าต้องรอครบทุกครั้งหรือไม่?
1) ถ้าข้อมูลพร้อมหลัง 2 วินาที test ต้องรอจนครบ 10 วินาทีหรือทำต่อได้ก่อน อธิบาย
2) ถ้าครบ 10 วินาทีแล้วยังไม่มีข้อมูล test จะทำต่อได้ตามปกติหรือเกิดข้อผิดพลาดจากการรอครบเวลา
ข้อมูลพร้อมหลัง 2 วินาที: test สามารถทำงานบรรทัดต่อไปได้ทันทีหลังจาก 2 วินาที ไม่ต้องรอจนครบ 10 วินาที  
 ครบ 10 วินาทีแล้วยังไม่มีข้อมูล: จะเกิดข้อผิดพลาด (เช่น TimeoutException) เพราะรอจนครบเวลาสูงสุดแล้วเงื่อนไขก็ยังไม่เป็นจริง

4.1 เว็บเวอร์ชันใดรับ 4 หน่วยกิต ทั้งที่กติกาให้รับได้แค่ 1-3?
1) คัดลอก Expected, Actual และ Status ของทั้งสามเวอร์ชัน
2) ระบุว่าเวอร์ชันใดทำผิดกติกา และทำผิดอย่างไร โดยอ้าง Actual ของเวอร์ชันนั้น
buggy: Expected = CREDITS_OUT_OF_RANGE / Actual = REGISTERED / Status = EXPECTED_FAIL   
fixed: Expected = CREDITS_OUT_OF_RANGE / Actual = CREDITS_OUT_OF_RANGE / Status = PASS   
refactored: Expected = CREDITS_OUT_OF_RANGE / Actual = CREDITS_OUT_OF_RANGE / Status = PASS   
เวอร์ชันที่ทำผิดและสิ่งที่ผิด: เวอร์ชัน buggy ทำผิดกติกา เพราะยอมรับการลงทะเบียน (Actual เป็น REGISTERED) ทั้งที่ควรจะปฏิเสธ (ควรเป็น CREDITS_OUT_OF_RANGE)

4.2 หลังจัดโครงสร้างโค้ดใหม่ เว็บยังปฏิเสธค่า 4 ได้เหมือนเดิมหรือไม่?

2) Lab 4 ลองเฉพาะค่า 4 เรายืนยันได้หรือยังว่าเวอร์ชัน refactored รับค่า 1 และ 3 ได้ถูกต้อง เพราะอะไร
ผลของ fixed เทียบกับ refactored: ได้ผลเหมือนกัน คือเว็บสามารถปฏิเสธค่า 4 และตอบกลับมาเป็น CREDITS_OUT_OF_RANGE ได้อย่างถูกต้องทั้งคู่

5.1 ค่า 0, 1, 2, 3 และ 4 ค่าไหนเว็บรับ และค่าไหนเว็บปฏิเสธ?
1) สำหรับแต่ละค่า ให้บันทึก Actual, Status และบอกว่าเว็บรับหรือปฏิเสธข้อมูล
2) ถ้าทดลองเฉพาะค่า 2 เราจะรู้หรือไม่ว่าเว็บมีปัญหารับค่า 4 เกินกติกา เพราะอะไร
ค่า 0: Actual = CREDITS_OUT_OF_RANGE / Status = PASS / เว็บปฏิเสธข้อมูล   
ค่า 1: Actual = REGISTERED / Status = PASS / เว็บรับข้อมูล  
ค่า 2: Actual = REGISTERED / Status = PASS / เว็บรับข้อมูล   
ค่า 3: Actual = REGISTERED / Status = PASS / เว็บรับข้อมูล   
ค่า 4: Actual = CREDITS_OUT_OF_RANGE / Status = PASS / เว็บปฏิเสธข้อมูล   
ถ้าลองเฉพาะค่า 2 จะรู้ปัญหาของค่า 4 หรือไม่: ไม่รู้ เพราะค่า 2 เป็นข้อมูลที่ถูกต้องและอยู่ในขอบเขต (Positive Test) การทดสอบแค่นี้ไม่สามารถบอกได้เลยว่าถ้าระบบเจอข้อมูลที่ผิดกติกา (เช่น ค่า 4) ระบบจะสามารถป้องกันหรือปฏิเสธได้หรือไม่

5.2 คุณอยากทดลองข้อมูลแบบใดเพิ่มอีก 1 กรณี?
1) ระบุข้อมูลให้ครบ: ชื่อ วิชา หน่วยกิต และติ๊กยืนยันหรือไม่
2) บอกว่าเว็บควรรับหรือปฏิเสธ พร้อมระบุข้อความตอบกลับที่คาดไว้
3) อธิบายเหตุผลโดยใช้กติกาของเว็บ กรณีที่เสนอควรต่างจากกรณีเดิมใน Lab 2 และ Lab 5
ชื่อที่จะกรอก: CE Student / วิชา: testing / หน่วยกิต: 2.5 / ติ๊กยืนยันหรือไม่: ติ๊ก   
เว็บควรรับหรือปฏิเสธ: ควรปฏิเสธ / ข้อความที่คาด: CREDITS_OUT_OF_RANGE   
เหตุผล: กติกาของเว็บคือต้องเป็น "จำนวนเต็ม" ตั้งแต่ 1 ถึง 3 การกรอก 2.5 จึงไม่ควรผ่าน (ซึ่งต่างจาก Lab 5 ที่ทดสอบเฉพาะจำนวนเต็ม) 

6.1 สองกรณีนี้ไม่ผ่านด้วยสาเหตุเดียวกันหรือไม่?
1) สำหรับ immediate_lookup บอกว่าปัญหาเกิดจากวิธีรอของ test หรือการตรวจหน่วยกิตของเว็บ พร้อมยกหลักฐาน 1 อย่าง
2) สำหรับ credits_4_buggy บอกว่าปัญหาเกิดจากวิธีรอของ test หรือการตรวจหน่วยกิตของเว็บ พร้อมยกหลักฐาน 1 อย่าง
3) สรุปสั้น ๆ ว่าทั้งสองกรณีมีสาเหตุเหมือนหรือต่างกันอย่างไร
immediate_lookup (Lab 3): สาเหตุ = เกิดจากวิธีรอของ test script ที่สั่งให้ค้นหาองค์ประกอบทันทีโดยไม่รอให้ข้อมูลปรากฏบนหน้าเว็บ / หลักฐาน = เกิดข้อผิดพลาด EarlyLookupFailure หรือ NoSuchElementException ใน Traceback   
credits_4_buggy (Lab 4): สาเหตุ = เกิดจากบั๊กของเว็บเวอร์ชัน buggy ที่ทำงานผิดกติกา / หลักฐาน = Actual ในรายงานแสดงผลเป็น REGISTERED ทั้งที่ Expected ระบุว่าควรเป็น CREDITS_OUT_OF_RANGE   
สาเหตุเหมือนหรือต่างกันอย่างไร: ต่างกันโดยสิ้นเชิง กรณีแรก test fail เพราะสคริปต์ทดสอบทำงานผิดจังหวะ (เขียน test ไม่ดี) ส่วนกรณีที่สอง test fail เพราะตัวแอปพลิเคชันมีบั๊กจริงๆ (test เขียนมาถูกแล้ว แต่ระบบทำงานผิด)
